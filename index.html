1.7 / LOAD预测 / 天气归因

1.7 天气变化不是自动根因

结论：欧洲天气确实有明显周变化，但坏站小样本不支持“升温就是主因”。

检查项结论
欧洲整体天气上周温度比上上周高约 5.50 摄氏度，体感高约 7.08 摄氏度。
短波辐射整体升高约 17.55%。
低分站小样本升温幅度和准确率下降没有明显相关性。
正确做法把天气变化按国家、模型、站点、坏站日对齐后再定责。
说人话：天气可以是线索，不能是借口。归因要回到站点和预测日。

2.2 / PV预测 / 数据和 NWP

2.2 NWP 对齐决定上限

结论：PV 没有未来天气就没有高上限；NWP 错配比模型小改更致命。

数据口径

2.7 / PV预测 / 积雪/融雪

2.7 积雪/融雪是一组覆盖规则

结论：snow-on 负责雪天压低虚高，snow-off 负责雪后恢复，二者都要写清楚名单、触发条件和最后写入。

积雪/融雪细分链路
01:15 峰值近 45 天历史最大 PV
20:45 snow-listECMWF 天气码 + 实发 PV
snow-on提前 5%，延续 3%
snow-off 候选过去 7 天名单 - 今天名单
TimeXer 重跑好天气历史日重构 2016 点
覆盖写入select_best_7 / Redis / Kafka
子项口径
snow-list用 ECMWF、历史最大 PV、当天实发 PV 识别；名单必须可复盘。
snow-on读取已有日前曲线，提前积雪压到历史最大 PV 的 5%，延续积雪压到 3%。
snow-off过去 7 天 snow-list 减去今天 snow-list，再加人工配置；明天温度、辐射、天气码转好才重跑。
历史重构选择 7 个好天气历史日，重构 2016 点输入，再跑 TimeXer。
输出写 snow_off_pv_dayahead、select_best_7、pv-dayahead-select-best-7。
坑点低 PV 可能是故障、限发或遮挡；注释比例和实际比例要一致；snow-off-list 要有 TTL。
2.8 / PV预测 / clipping

2.8 clipping 是覆盖链路

结论：clipping 不参与常规 `select_best_7` 排名，而是在后续调度里覆盖最终结果。

场景正确口径
sub_working_mode=0走 6 源 clipping，模型用 `Timexer-pv-dayahead-mae-mape`。
sub_working_mode=1走 EC 单源 clipping，模型用 `Timexer-pv-dayahead-ec-mae-mape`。
审计模型名6 源写 `...-clipping`，EC 写 `...-ec-...-clipping`。
最终输出仍写 `pv-dayahead-select-best-7` 和 `select_best_7`。
AUS `82026051100229` 的问题是 sub=0 站点被 sub=1 过滤挡掉，不是常规日前预测没写。

第3章：AI算法平台

本章导语

AI 算法平台不是训练脚本集合。它要把数据、实验、指标、模型资产、上线复盘和文档沉淀做成闭环。

3.1 平台功能数据工厂、实验编排、MLflow、排行榜。
3.2 数据工厂统一 raw、cleaned、feature、dataset。
3.3 实验自动化smoke、50k pilot、full、远程 GPU。
3.4 MLflow 和榜单指标、产物、模型对比。
3.5 模型资产checkpoint、量纲、输入输出、回滚。
3.6 多 Pod 推理站点分片、worker 微批、压测。
3.7 自动化上限平台能执行，不能替你定义正确问题。

3.9 自动化成熟度L0 到 L5，看平台现在差在哪。
3.1 / AI算法平台 / 功能

3.1 平台要做成闭环

平台主线
数据工厂清洗、增强、构建数据集
实验编排smoke / pilot / full
MLflow参数、指标、产物
排行榜模型对比和目标状态
模型封装checkpoint 和推理接口
复盘问题回流下一轮

`D:\sigen_ai\docs\sessions` 要进入平台知识库。它记录为什么这样改，不是临时聊天记录。

3.2 / AI算法平台 / 数据工厂

3.2 数据工厂要统一口径

结论：没有统一数据层，训练、生产、排查会各说各话。

数据标准链路
raw原始入库和时间戳
cleaned缺失、异常、单位
feature天气、日历、画像
dataset切分、mask、hash
DQ report质量评分和变更记录
  • PV `/100`、Load `filtered_load_power / 60 * 5` 这类量纲要进字典。
  • 特征版本、数据版本、配置 hash 要进入实验报告。
  • 预处理逻辑不能分散在平台、PV、Load 三个仓库里各写一套。
3.3 / AI算法平台 / 实验自动化

3.3 先筛方向，再跑 full

结论：平台要阻止“并发堆满 GPU 跑无效 full”的低质量实验。

阶段作用
smoke检查代码、shape、loss、预测数组是否正常。
50k pilot用 strict 口径筛方向，过 gate 再继续。
full只给强候选，完整指标和产物必须落盘。
诊断桶分析、曲线、bad case、偏差和能量指标。
GPU 调度要先看占用，不抢非本任务进程。平台要记录每个 started、blocked、failed、completed 实验。
3.4 / AI算法平台 / MLflow 和榜单

3.4 榜单不能只看一个数

结论：RMSE_ACC 只是主指标，不能掩盖 MAPE、能量偏差和正负偏差。

字段为什么要记录
RMSE_ACC / MAPE_ACC主指标和业务感知指标。
daily_energy_mae日总量误差，防止曲线形状好但能量错。
daily_energy_bias区分系统性高估或低估。
pos_dev / neg_dev控制正负偏差平衡。
预测数组路径后续 bad case 不用重跑全量推理。
3.5 / AI算法平台 / 模型资产

3.5 模型上线要交付证据包

结论：checkpoint 不是完整模型资产。上线要能解释输入、量纲、后处理和回滚。

输入规范张量 shape、天气源、变量顺序、缺失填补。
量纲规范训练目标、线上写入、是否反归一化。
后处理规范day mask、非负裁剪、DST/WST、quiet-day。
追踪规范短名/长 tag 映射、checkpoint、配置 hash。

PV 的 targetnorm TFT 和 LightGBM 接入说明了这点：量纲和 model_name 写错，会把好模型变成线上坏 case。

3.6 / AI算法平台 / 多 Pod 推理

3.6 百万站点不能单 Pod 串行

结论：定时预测走 Indexed Job 分片，外部触发走 worker 微批，两条链路共用同一套 batch 预测代码。

PV 大规模推理架构
CronJob45 万定时站点
Indexed Jobhash(site_id) 分片
Worker5 万外部触发
Batch predictPod 内批量特征和推理
幂等 upsert失败可重跑

初始参数可以是 120 shards、20 并发 Pod。压测必须记录 batch 特征耗时、predict 耗时、upsert 耗时和 P95/P99。

3.7 / AI算法平台 / 自动化上限

3.7 平台不能替代问题定义

结论：完全 AI 算法自动化部署目前做不到。平台能自动执行，但不能自动保证方向正确。

不能完全自动化原因
问题定义预测目标、horizon、指标权重需要业务判断。
数据归因设备故障、限发、天气错配、积雪需要人工确认。
验证集构造合法同分布、无泄漏验证集不是自动生成就可信。
上线决策精度、吞吐、维护、回滚和风险要一起看。
3.8 / AI算法平台 / 当前缺口

3.8 短板要写成待办，不要写成愿景

缺口影响
预处理逻辑分散训练和生产口径不一致，外部审阅难解释。
Load QC 不统一质量报告说服力弱。
配置 hash 不统一复现实验证据弱。
预测资产保存不稳定bad case 只能重跑。
短名/长 tag 映射分散Kafka 和 StarRocks 排查容易看错。
推理压测缺标准报表无法证明 10 万+ 到百万站点吞吐。

3.9 / AI算法平台 / 自动化成熟度

3.9 现在还不是完全自动部署

结论：平台当前在 L2 到 L3。能自动跑实验、沉淀指标和资产，但坏例归因、上线判断、回滚阈值还不能交给系统自己拍板。

等级状态平台当前位置
L1 可复现固定配置能重跑。生产上线部分还在这里。
L2 自动编排smoke、pilot、full 自动跑。实验编排主状态。
L3 自动评估MLflow、榜单、预测资产自动沉淀。排行榜和证据包在接近这里。
L4 半自动准入精度、吞吐、回滚是硬 gate。下一阶段目标。
L5 完全自动部署系统自动定义问题并上线。当前不到。
能自动构建数据、跑实验、记指标、出榜单、保存预测资产。
不能自动判断业务目标、验证集合法性、NWP/设备/积雪真根因。
下一步数据字典、实验门禁、模型证据包、压测模板、上线 gate。
判断标准平台把证据摆全，人负责最后上线责任。
